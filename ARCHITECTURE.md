# MailMind — Architecture & Technical Design

> **Status:** This document describes the intended target architecture. The current codebase does not yet implement the authentication, persistence, live integrations, frontend, or production safeguards shown below. See `README.md` for the verified local-demo scope.

## 1. System Overview
MailMind is an agentic productivity system that orchestrates multi-agent workflows to inspect emails, query calendar appointments, synthesize information with semantic memory, and execute approved user actions.

## 2. LangGraph State Machine Specification

The state is defined using Python's `TypedDict` and `Annotated[list, add_messages]`:

```python
from typing import Annotated, TypedDict, List, Dict, Any, Optional, Literal
from langgraph.graph.message import add_messages

class PlanStep(TypedDict):
    step_id: int
    tool: Literal["gmail", "calendar", "rag", "memory"]
    action: str
    args: Dict[str, Any]
    status: Literal["pending", "running", "completed", "failed"]
    result: Optional[str]

class MailMindState(TypedDict):
    # Core conversational messages with automatic reducer
    messages: Annotated[list, add_messages]
    
    # Active user context
    user_id: str
    thread_id: str
    user_preferences: Dict[str, Any]
    
    # Plan generated by the Planner
    plan: List[PlanStep]
    current_step_index: int
    
    # Retrieved evidence for citations
    retrieved_emails: List[Dict[str, Any]]
    retrieved_events: List[Dict[str, Any]]
    retrieved_memories: List[Dict[str, Any]]
    
    # Action awaiting human approval (HITL)
    pending_action: Optional[Dict[str, Any]]
    action_approved: Optional[bool]
    
    # Final formatted response with sources
    final_response: Optional[str]
```

### 2.1 Graph Node Descriptions
1. **`planner_node`**: Decomposes user request into explicit sub-tasks.
2. **`gmail_tool_node`**: Calls Gmail API v1 (Search, Read, Fetch Thread, Draft).
3. **`calendar_tool_node`**: Calls Google Calendar API v3 (Search, Conflict Check, Schedule).
4. **`rag_retrieval_node`**: Performs dense + lexical hybrid search over stored `email_chunks`.
5. **`memory_retrieval_node`**: Fetches user preferences and historical entities from `user_memories`.
6. **`synthesizer_node`**: Formulates reasoning across all evidence and crafts response.
7. **`evidence_verifier_node`**: Verifies every claim against retrieved data and assigns citation badges.
8. **`hitl_interrupt_node`**: Invokes `langgraph.types.interrupt()` if an email send or calendar change is required.

## 3. Storage & Data Persistence Architecture

### 3.1 PostgreSQL + pgvector
- **Engine:** PostgreSQL 16 with official `pgvector/pgvector:pg16` Docker image.
- **ORM:** SQLAlchemy 2.0 (asyncio) + Alembic for migrations.
- **Vector Search:** Cosine similarity (`<=>`) with IVFFlat or HNSW index for sub-millisecond retrieval across tens of thousands of email chunks.

### 3.2 Redis Cache & Message Queue
- **Session Tokens:** Caches temporary OAuth state tokens and active user JWT blocklists.
- **Background Sync Workers:** Celery / ARQ worker queue for async ingestion of emails from Gmail API into pgvector.

## 4. Security & Privacy Architecture
1. **OAuth Security:** Standard Authorization Code Flow with PKCE. Tokens never exposed to client-side cookies or localStorage.
2. **Data Encryption at Rest:** Google Refresh Tokens and Access Tokens stored with AES-256-GCM symmetric encryption using an application master secret key (`TOKEN_ENCRYPTION_KEY`).
3. **Data Isolation:** Every database query enforces `WHERE user_id = :current_user_id` multi-tenancy boundaries.
4. **Least Privilege API Scopes:** Only request scopes necessary for requested features. Default to read-only during initial sign-in.
